# Octagon · Mastrena Parts Catalog

Internal catalog of Mastrena II spare parts for Octagon Services (Vancouver, BC). The app is a single `index.html` file, with no build step and no server. Its data comes from `data/parts.csv`.

## What it does

- Shows only parts that have been verified (see below). The header counts them.
- Shows the catalog as a compact list: a sketch, the English and Spanish names, SKU and price. Tap a row to open its details; the actions (edit, label, remove) live there.
- Searches by name or SKU. Module tabs show counts, and you can also filter by subassembly (the manual's numbering, for example 1.10.2 Brew module), "No price".
- Sorts by manual order, SKU, name or price.
- Adds, edits (including price) and removes parts. Removing asks for confirmation inside the page.
- Selects several parts at once and sets or clears their price in one step.
- Shows two quantities per part in the opened row, as a sample for the database stage: **On hand** (a counter with - and + buttons) and **Per machine** (how many the machine uses). The header shows the total number of parts. Per-machine values are filled only for the 19 main assemblies listed on page 3 of the manual; everything else is blank until the next stage. Both numbers are saved in this browser only and travel in the CSV (`on_hand`, `qty_per_machine`).
- Suggests the translation of a part name while you type it: write the English name and the Spanish one fills in, or the other way around. The suggestion is marked so it can be checked, and a name someone typed by hand is never overwritten (see Translation below).
- Exports and imports the catalog as CSV. Import checks the columns and duplicate SKUs before it replaces anything.
- Shows the bag label of each part as a picture in the opened row, to the right of the details. Click it to enlarge it, choose the quantity and copies, and print.
- Prints bag labels in the style of the Thermoplan ones: the Article no. in large type, the English and Spanish names, the quantity in the bag, a CODE128 barcode of the SKU, and the Octagon logo down the left side. You choose the quantity and the number of copies. They print at 4 × 2.4 in. The logo is an octagon with the word "Octagon" in script, drawn in code (`LOGO_SVG` in `index.html`); replace it with the final artwork when you have the file.
- In each opened part, two buttons set its approval state: **Hand-checked** (green) and **Needs hand check** (amber). The row changes color at once and the counts update. There is no login yet, so anyone can press them; the choice is saved in this browser and survives a reload. Export the CSV (it carries the `validation` and `evidence` columns) to keep or share it. To make a hand check permanent for everyone, add the SKU to `data/manual_validations.txt` and run `python data/build_parts.py`.
- The list opens on **All**: every part (403), colored for the double check. Green = hand-checked against the paper manual, amber = still needs the hand check (verified by the automatic reading only, or not verified yet). The header counts each group; the tabs All / Hand-checked / Needs hand check filter them. `data/parts_review.csv` holds this data (generated by `data/build_parts.py`). Team mode (`?validate`, local copy) adds the confidence, the real evidence and bulk verify.
- A part can have extra views next to its main image (`img/<sku>-<view>.jpg`, listed in `EXTRA_VIEWS` in `index.html`). Today 128.047 and 128.386 show their exterior as the main image and the mechanism as an extra view; it shows in the opened row and can be enlarged too.
- Tap a SKU in the list to copy it (dotted underline), or use the "Copy" buttons in the opened row for the SKU and the 8-digit number. It shows a "Copied" message.
- Shows an image for some parts: a real photo (140.763) or an illustration generated from a photo of the part, marked **Illustration**, and a shared tube image marked **Generic image** for FEP pipes and a name-based generic image for parts without a photo, such as screws, nuts, O-rings, belts, connectors, valves and assemblies, listed in `GENERIC_SKUS` in `index.html` (they show the type of part only; length, diameter and shape vary by SKU; the dimensions in the name are the real ones). Add an image as `img/<sku>.jpg` and list the SKU in `PHOTOS` in `index.html`. Click the small image in the list, or the larger one in the opened row, to see it enlarged (Esc or a click outside closes it). Parts with their own image always come first in the list (then the ones with a shared tube image), whatever the sort; the chosen sort applies inside each group.
- Draws a hand-style sketch for each part. These are representative drawings by part type (screw, O-ring, valve, ...), chosen by keywords in the English name. They are not photos of the exact part.
- Works on phones (designed for 400px wide) and follows the device's light or dark mode.

**Important:** changes are saved in this browser only (localStorage, key `octagon-inv-v1`). Each device keeps its own copy, so export the CSV after editing.

## Publish on GitHub Pages

1. Create a GitHub repository and push this project (`git remote add origin ...`, then `git push -u origin master`).
2. On GitHub, go to **Settings → Pages**.
3. Under **Source**, choose *Deploy from a branch*, branch `master`, folder `/ (root)`, and save.
4. After about a minute the app is live at `https://<user>.github.io/<repo>/`.

The first time someone opens the page, the app loads `data/parts.csv`. From then on it uses that person's local copy. Each time the page is opened it also checks `data/parts.csv` for parts that are new since that browser's last visit and adds them (a toast says how many). A part that was removed on purpose is not brought back. The first time an older copy syncs, parts that were removed before will come back once.

> Opening `index.html` by double-clicking it (`file://`) won't work: the browser blocks reading `data/parts.csv`, so the app starts empty. Use **Import CSV** and pick `data/parts.csv`, or test locally with `python -m http.server` and open `http://localhost:8000`.

## How parts become verified

The published catalog contains only verified parts. A part is verified when a second, independent source agrees with the first reading. `data/build_parts.py` applies this rule:

1. The same Article no., 8-digit SKU and name were read identically on 2 or more clear pages, or
2. The name equals the title of the part's own chapter in the manual (the SKU was read once).

In both cases the Article no. must look like `NNN.NNN`, the 8-digit SKU must look like `11xxxxxx` and belong to no other article, and the manual must not have a typo flagged on that part. This is a cross-check of the reading, not a guarantee: the paper manual is still the final authority.

Everything else waits to be validated. That list is internal and is not published: the build writes it to `data/internal/` (ignored by git), together with a report of the rows to check. To work through it:

- Run the app locally (`python -m http.server`) and open `http://localhost:8000/?validate`. That mode shows the **Catalog** and **To validate** views, the evidence for each part, and the **Mark verified** buttons. It keeps its own saved copy, separate from the normal one.
- After checking a part against the paper manual, add its Article no. to `data/manual_validations.txt` and run `build_parts.py`. The part moves into `data/parts.csv`, and the next push publishes it.

The status is kept in two columns of `data/internal/parts_all.csv`: `validation` (`verified` or `pending`) and `evidence` (a short sentence). They are not in the published CSV.

## Translation

When you add or edit a part, typing in **Name (EN)** fills **Name (ES)** with a suggestion, and typing in **Name (ES)** fills **Name (EN)**. A note under the field says where the suggestion came from, and lists the words it could not translate. Anything a person has typed by hand is left alone.

Suggestions come from these sources, in this order:

1. **A part already in the catalog** with the same name: its other-language name is reused.
2. **The glossary**, `data/glossary.csv`, plus a few grammar rules (adjectives go after the noun, "water pump cover" becomes "tapa de bomba de agua", sizes keep their form, decimal points become commas). It works without internet and always uses the same vocabulary as the rest of the catalog.
3. **A translation service (AI), not connected yet.** It is only asked when the glossary finds words it doesn't know.

How good is it? Measured against the 403 names already translated by hand, the glossary gives the same name in about 7 of 10 English-to-Spanish cases and 6 of 10 Spanish-to-English (ignoring the word "de"). The rest are wording or word-order differences, or words that aren't in the glossary yet. Treat every suggestion as a draft.

**Adding words.** Open `data/glossary.csv` and add a line: `en,es,pos,gen`.

- `pos`: `N` noun, `U` fixed phrase (used as a noun, never reordered), `A` adjective (put in front in English), `AP` adjective that follows the noun in the manual ("module left"), `AI` adjective that doesn't change with gender, `X` word that is only swapped (with, for, and).
- `gen`: `m` or `f`, for nouns and phrases. Adjectives agree with it.
- End `pos` with `>` to use the line only English to Spanish, or `<` for Spanish to English only. A `<` line is written the other way round: `spanish,english`.
- When two lines have the same English text, the first one is used for English to Spanish, and the first Spanish match is used for Spanish to English.

**Connecting the AI service later.** The page already has the hook. In `index.html`, set `TRANSLATE_REMOTE_URL` to the address of a small server function (for example a Supabase Edge Function). The page then sends a POST with JSON like

```json
{ "text": "Brass heating element 230V", "from": "en", "to": "es", "draft": "Element de heating de brass 230V", "unknown": ["Element", "heating", "brass"] }
```

and expects `{ "text": "Resistencia calefactora de latón 230V" }` back. It is only called when the glossary has unknown words, and if it fails the glossary draft is used. The API key must live on the server, never in the page: the repository is public.

## Update the catalog

**Changes made in the app** (prices, corrections):
1. In the app, click **Export CSV**.
2. Replace `data/parts.csv` with the exported file and commit it. People opening the page for the first time will see the new version.
3. Anyone who already has a local copy updates it with **Import CSV**.

**Re-extract from the manuals:**
1. Fix `data/transcription_A.txt`. Each page starts with `## image_no|file|section|module` and each row is `article|sku8|description`.
2. If you add a new part, add its Spanish name to `data/translations_es.py`.
3. Run `cd data && python build_parts.py`. This regenerates `parts.csv` (verified parts only) and, in `data/internal/`, `parts_all.csv` and `extraction_report.md`.

Re-extracting overwrites any prices in `parts.csv`. Once prices are loaded, edit them in the app instead.

## Files

- `index.html`: the app.
- `data/parts.csv`: the published catalog (UTF-8 with BOM so Excel shows accents correctly). It has only the columns people use: `sku`, `sku_8digit`, `page` (printed page of the manual where the part is listed; its diagram is on the next page), `name_en`, `name_es`, `module`, `subassembly`, `price_cad`, `qty_per_machine`, `on_hand`, `notes`. The CSV that people export from the app has the same columns. The development columns live in `data/internal/parts_all.csv`. `name_es` is a translation made by Claude, not text from the manual. In `data/internal/parts_all.csv`, `source_image` and `diagram_position` point back to the source photo. `confidence` (the confidence of the reading) is the same kind of field. These are for the team only. The app shows them only in team mode (`?validate`), and only team mode exports them in the CSV. Regular users never see them, and their exported file does not contain them.
- `data/glossary.csv`: English and Spanish terms used to suggest translations.
- `data/transcription_A.txt`: the manual's parts tables, transcribed page by page.
- `data/build_parts.py` and `data/translations_es.py`: build the CSV files and the report.
- `data/manual_validations.txt`: Article numbers checked by hand against the paper manual.
- `data/internal/`: local only, not committed (all parts, the report and the pilot).
- `CLAUDE.md`: instructions for the development agent (scope, data rules, what stays internal). It is public, so it carries no names of people or of the client.
- `IDEAS.md`: ideas outside the current scope.

The manual images are not committed to the repository.
